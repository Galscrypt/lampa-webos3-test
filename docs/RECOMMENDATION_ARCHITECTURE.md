# Compact Smart — архитектура рекомендаций

## Целевой результат

Главная должна отвечать на четыре разных вопроса:

1. Что с высокой вероятностью понравится именно этому пользователю?
2. Что качественного вышло недавно?
3. Что хорошего пользователь мог пропустить?
4. Что доступно в выбранных им стримингах?

Один универсальный список эти задачи не решает. Ядро строит общий пул
кандидатов, а каждый ряд применяет собственный intent и веса.

## Конвейер

```text
Favorite + Timeline + Timetable + настройки
                    |
                    v
          локальный профиль вкуса
                    |
                    v
 recommendations + discover + trending + providers
                    |
                    v
       нормализация и жёсткие фильтры
                    |
                    v
     quality score + relevance + freshness
                    |
                    v
       diversity + межрядовая дедупликация
                    |
                    v
          ряды Lampa + bounded cache
```

Каждый этап должен быть отдельной чистой функцией, доступной тестам. Сетевой код
не должен одновременно решать фильтрацию или ранжирование.

## 1. Снимок пользователя

### Источники

| Сигнал Lampa | Значение для профиля | Исключение из выдачи |
| --- | --- | --- |
| `like` | сильный положительный | нет |
| `wath`, `book` | намерение посмотреть | нет |
| завершённый фильм в `history`/Timeline | положительный, если не брошен | да |
| частично просмотренный фильм | слабый/нейтральный; зависит от прогресса | обычно да из рекомендаций, остаётся в «Продолжить» |
| `continued`, `scheduled` | сильный интерес к сериалу | нет, если есть новые серии |
| полностью просмотренный сериал | положительный профиль | да |
| `thrown` | отрицательный | всегда да |
| `look`, `viewed` | слабый положительный либо нейтральный | зависит от фактического Timeline |

Профиль строится раздельно для `movie` и `tv`. Карточка получает стабильный ключ
`media_type:id`; для данных без `media_type` тип выводится по `first_air_date`,
`name` и `original_name`.

### Вес свидетельства

Начальные собственные коэффициенты, которые обязаны пройти fixture-тесты и
последующую калибровку:

| Событие | Вес |
| --- | ---: |
| `like` | +2.4 |
| просмотрено >= 80% | +1.5 |
| `continued`/`scheduled` | +1.2 |
| `wath`/`book` | +0.7 |
| просмотрено 30–79% | +0.3 |
| начато < 15 минут | 0 |
| брошено после 15 минут и до 30% | -0.4 |
| `thrown` | -2.5 |

Если Lampa не отдаёт время/длительность, используется только процент и категория.
Давность ослабляет сигнал с half-life 90 дней, но не ниже 20% исходного веса.
Положительные и отрицательные признаки хранятся раздельно, чтобы одна
случайность не уничтожала устойчивый интерес.

### Признаки v1

Обязательные без дополнительных запросов:

- genre ids с позиционным весом `1.0 / 0.75 / 0.5`;
- язык и страна, если они уже присутствуют;
- десятилетие релиза;
- тип контента.

Ограниченное обогащение только для 6 самых сильных seeds каждого типа:

- keywords;
- до 3 ведущих актёров;
- режиссёр фильма или creators сериала;
- runtime;
- production countries.

Метаданные seed-карточек кэшируются на 30 дней. При их отсутствии алгоритм
остаётся полноценным на жанрах и эпохах.

### Уровни холодного старта

- `0–2` надёжных seeds: quality + trending, без мнимой персонализации.
- `3–9`: жанры, эпоха и отрицательные исключения.
- `10+`: полный профиль и персональные ряды.

## 2. Кандидаты

Начальный общий бюджет одного обновления — не более 6 TMDB-запросов, максимум 2
одновременно:

1. recommendations от лучшего movie seed;
2. recommendations от лучшего TV seed;
3. профильный discover для фильмов;
4. профильный discover для сериалов;
5. trending movie;
6. trending TV.

Два seeds одного типа можно чередовать по дням, а не запрашивать одновременно.
Провайдерская категория загружается только при открытии или если пользователь
явно включил ряд «В моих подписках». Пул ограничен 80 карточками на тип.

Discover использует максимум три доминирующих жанра через OR (`|`). Жёсткий AND
между всеми любимыми жанрами создаёт узкую и повторяющуюся выдачу. Keywords и
люди добавляются отдельным запросом только на следующем этапе развития.

Каждый кандидат хранит provenance: `seed`, `profile`, `trending`, `provider`.
Повтор из нескольких независимых источников даёт небольшой confidence-бонус,
но не удваивает карточку.

## 3. Жёсткие фильтры

До scoring исключаются:

- нет id, названия или постера;
- `adult=true` и запрещённые ключевые слова;
- `thrown`;
- просмотренный фильм;
- сериал, у которого просмотрены все уже вышедшие эпизоды;
- ещё не вышедший релиз, кроме отдельного ряда «Скоро»;
- дубль по `media_type:id`;
- контент вне включённых возрастных ограничений;
- provider-карточка вне выбранного `watch_region`;
- карточка ниже динамического минимального доверия.

Порог доверия не должен быть одним для всех лет. Для свежих релизов допустимо
меньше голосов; для старого каталога требуется больше:

| Возраст релиза | Movie min votes | TV min votes |
| --- | ---: | ---: |
| до 180 дней | 30 | 20 |
| 180 дней – 3 года | 100 | 60 |
| старше 3 лет | 250 | 120 |

Это стартовые значения. Локальному русскоязычному контенту разрешается 50%
порога, но только при достаточной Bayesian quality — послабление не означает
автоматический подъём в топ.

## 4. Оценка качества и релевантности

### Байесовский рейтинг

Сырой TMDB-рейтинг заменяется на:

```text
WR = v / (v + m) * R + m / (v + m) * C
```

где `R` — `vote_average`, `v` — `vote_count`, `C` — средняя оценка пула, `m` —
минимальное доверительное число голосов для возраста и типа карточки. Это не
даёт сериалу с оценкой 9.8 и пятью голосами обойти проверенную карточку.

### Нормализованные компоненты

- `profile`: совпадение положительных жанров, keywords, людей, эпохи и языка
  минус отрицательные признаки;
- `quality`: нормализованный WR;
- `freshness`: плавное затухание, а не ступенчатый бонус по году;
- `confidence`: логарифм числа голосов и подтверждение несколькими источниками;
- `availability`: бонус только в provider-ряду;
- `novelty`: небольшой бонус карточкам вне самого популярного хвоста.

Вес по умолчанию для персонального ряда:

```text
score = 0.38*profile + 0.27*quality + 0.12*freshness
      + 0.08*confidence + 0.08*availability + 0.07*novelty
```

Это стартовая гипотеза, а не константа навсегда. В cold start вес `profile`
перераспределяется в `quality`, `confidence` и `freshness`. Для «Скрытых
жемчужин» растёт `novelty`; для «Новых достойных» — `freshness`; для «Лучшее за
всё время» freshness равен нулю.

## 5. Диверсификация

Сортировка только по score почти неизбежно создаст десять криминальных драм
подряд. Из первых `3*K` кандидатов строится итоговый ряд жадным re-rank:

- не более 3 карточек одного primary genre в первых 10;
- не более 2 карточек одной франшизы/collection в первых 10, если поле известно;
- не более 2 карточек одного режиссёра/creator в первых 10;
- не более 60% одного языка/страны, кроме специализированного ряда;
- минимум 2 discovery-слота на 20 карточек, только если WR прошёл quality gate;
- штраф за карточку, уже попавшую в более приоритетный ряд на главной.

Для стабильной навигации равные карточки перемешиваются детерминированно по
ключу `дата + profile_signature + row_id`, поэтому порядок не прыгает при каждом
открытии и обновляется раз в день.

## 6. Состав главной

На слабом телевизоре одновременно нужны не десятки рядов, а четыре сетевых ряда
с ясной ролью плюс статическая навигация:

1. `Для вас — фильмы`.
2. `Для вас — сериалы`.
3. `Новые, которые стоит смотреть`.
4. Один ротируемый ряд: `Скрытые жемчужины`, `Похоже на ...`, тема недели или
   `В ваших подписках`.

`Продолжить просмотр` остаётся задачей самой Lampa. Разделы, жанры и логотипы
провайдеров остаются локальными навигационными рядами и не расходуют сеть.

## 7. Стриминги

Настройки должны хранить:

- регион пользователя (по умолчанию `RU`);
- выбранные subscriptions;
- допустимые типы `flatrate|free|ads`;
- отдельное включение аренды/покупки.

Каталог провайдера строится только через `with_watch_providers` вместе с
`watch_region`. `with_networks` применяется только к производителю/телесети
сериала. В UI сохраняется атрибуция JustWatch.

## 8. Кэш, производительность и отказ

- Общий candidate snapshot: 8 часов, stale 7 дней.
- Профиль: пересчёт по `state:changed`, debounce 2 секунды.
- Seed details: 30 дней, максимум 24 записи.
- Готовые ряды: ключ `profile_signature + settings_signature + day`.
- Первое отображение из свежего cache: синхронно, целевой бюджет <100 мс.
- Сеть: максимум 2 активных запроса, тайм-аут 6,5 секунды.
- Ошибка одного источника не отменяет остальные; при полном отказе отдаётся
  последний рабочий snapshot либо текущие неперсональные ряды.
- Ни один cache miss не должен оставлять главную бесконечно пустой.

Runtime остаётся ES5 и сохраняет лимит размера. Если интеллектуальное ядро не
умещается безопасно, оно выделяется во второй локально загружаемый файл с тем же
стабильным URL-контрактом; внешний сервер для вычислений не добавляется молча.

## 9. Наблюдаемость без слежки

Локальный debug-режим хранит только агрегаты:

- число seeds и кандидатов по источникам;
- причины отбраковки;
- latency и число запросов;
- доли жанров и источников в итоговом ряду;
- версию формулы и signature настроек.

Названия истории, токены и полный профиль не логируются и никуда не отправляются.
